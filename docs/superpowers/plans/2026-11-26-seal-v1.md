# Seal v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the Seal roadmap through a verified v1 release candidate with safe signed manifests, hardened keys, security regression controls, and independently verifiable cross-platform release artifacts.

**Architecture:** Extend the existing single Rust crate with manifest, capability-scoped filesystem, and release verification modules. Keep SHA-256, Ed25519, and OpenSSH SSHSIG; sign exact canonical manifest bytes under a separate namespace. Use fixed-parameter Argon2id + XChaCha20-Poly1305 key encryption and OS-specific protected key-file creation.

**Tech Stack:** Rust 1.96 stable, existing crates, `cap-std`, `argon2`, `chacha20poly1305`, `rpassword`, fuzzing via `cargo-fuzz`/libFuzzer, GitHub Actions, CycloneDX SBOM.

**Spec:** `docs/superpowers/specs/2026-11-26-seal-v1-design.md`

## Global Constraints

- Keep a single Rust crate and `#![forbid(unsafe_code)]` in first-party Rust.
- Verification is offline and always requires an explicitly supplied public key.
- Do not follow symlinks/reparse points or accept non-regular files in a manifest tree.
- Canonical manifest and signature inputs are versioned, strict, and bounded.
- Use established crypto libraries; add no custom crypto.
- Do not pass secrets to logs, command lines, CI variables, or untrusted workflows.
- Do not auto-publish the final v1 production release.

## Review Focus

- Windows path and reparse-point changes during traversal must not escape the opened root.
- Duplicate keys, duplicate/case-colliding paths, unsupported fields, and noncanonical JSON must fail before verification succeeds.
- Missing, modified, unexpected, unreadable, or changing files must never produce success.
- Wrong passphrases, truncated encrypted keys, and failed key creation must not leave a usable partial private key.
- Release provenance must describe the exact artifact digest and source repository/ref; credentials must not reach fork pull requests.

## File Structure

- `src/manifest.rs`: deterministic schema, canonical encoding, bounded parser, path policy, typed errors.
- `src/tree.rs`: capability-scoped enumeration, safe file opens, creation and exact verification.
- `src/signature.rs`: file/manifest object signing and verification, with domain separation.
- `src/keys.rs` (or focused additions to `signature.rs`): encrypted private-key I/O and permission policy.
- `src/main.rs`: CLI commands, stable JSON/human outputs and exit codes.
- `tests/manifest_cli.rs`, `tests/key_security.rs`, `fuzz/`: regression and fuzz coverage.
- `docs/`: exact manifest/signature/key/bootstrap/release specs, threat model, dependency review, benchmark and testing evidence.
- `.github/workflows/`: bounded fuzz, repeat-build, benchmark, and release-candidate workflows.
- `ROADMAP.md`, `SPEC.md`, `README.md`, `SECURITY.md`, `CHANGELOG.md`: status and v1 user contract.
